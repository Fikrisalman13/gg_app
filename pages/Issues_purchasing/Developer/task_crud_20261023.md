## Audit pra-edit

### Alur dan invariant

| Mutasi | Otorisasi server | Invariant dan penegakan |
| --- | --- | --- |
| Buat issue | `CanAdd` + CSRF | Tipe `Task`/`Support Activities`; status awal hanya `To Do`/`In Progress`; pasangan kategori-subkategori aktif dan konsisten; `request_id` unik per pembuat untuk retry idempoten. |
| Ubah issue | `CanEdit`, atau pembuat untuk quick-complete + CSRF | Status hanya `To Do`/`In Progress`/`Done`; `tanggal_selesai` ada hanya saat `Done`; predicate `row_version` menolak edit stale dengan `409`. |
| Hapus issue | `CanDelete` + CSRF | Menghapus satu issue dengan predicate `row_version`; request stale/row hilang menghasilkan `409`/`404`, bukan sukses semu. |
| Kategori/subkategori | `CanAdd`/`CanEdit`/`CanDelete` + CSRF | Nama unik; subkategori harus punya kategori aktif; hapus direject jika masih direferensikan oleh issue/template sesuai FK `NO ACTION`. |
| Template | Pemilik template + hak mutasi + CSRF | Template dibatasi pembuatnya; nama unik per pembuat; data referensi kategori/subkategori tervalidasi. |

### Bukti dan risiko relevan

- Metadata SQL Server read-only membuktikan PK/FK/unique index: `request_id` unik bersama `created_by`, `row_version` tersedia, dan FK kategori/subkategori memakai `NO ACTION`.
- Endpoint mutasi lama sengaja stub (`503`) dan UI aktif belum memuat form write. Artefak `modal_add_issue.php` dan `modal_edit_issue.php` adalah salinan legacy IT/Project/asset, sehingga tidak boleh diaktifkan kembali.
- Risiko kuat: tanpa CSRF, validasi pasangan kategori/subkategori, transaksi, idempotensi, dan rowversion, direct POST atau retry dapat membuat duplikasi/inconsistency. Implementasi wajib menutup semua entrypoint write baru.
- Runtime dengan data/sesi write nyata belum tersedia; success, rollback transaksi, konflik stale, dan duplicate retry akan tetap berstatus blocked sampai ada fixture/otorisasi uji yang aman.
